# Design decisions

- 2026-10-07: The guard lives in `start_implementation_status`, not in `wp_state` force semantics (C-003, avoids an ADR).
- 2026-10-07: A null review-result slot is read as "no verdict on record" (the reducer writes null only on an in_review exit with no verdict); a malformed slot still refuses.
- 2026-10-07: Forced non-arbiter approvals are skipped when picking the approval stamp (lenient fallback to the newest review approval) rather than poisoning the bound.
- 2026-10-07: The reducer's `implementer_of_record` stays (claim provenance, persisted gen-2 snapshot field); only the guard and consolidation readers converge on `review_roles`.
- 2026-10-07: `review_lane_exit` is an explicit opt-in held only by `agent action implement`; `spec-kitty implement` and orchestrator-api keep the old `WorkPackageStartRejected` for every review lane. `--force` is refused before any write unless the WP is in a review lane (done/canceled stay rejected), and `--force` needs `--agent` because the agent becomes the implementer of record.
- 2026-10-07: A `review_result: null` slot is now split by `ReviewResultLookup.cleared_without_verdict` (raw None = verdict-less review exit, treated as no verdict on record by the approval guard, both status boards and the approval-artifact writer) from a malformed slot (still fails closed). Accepted: a cleared slot hides an earlier cycle's rejection from the verdict facts; the events keep it.

## 2026-10-07 WP03 (#5340): one implementer-of-record authority
- Added `latest_implementer_event` to `status/review_roles.py` (exported from the `specify_cli.status` facade); `latest_implementer_actor` now delegates to it. Preflight reads the event's full recorded identity (not the tool-scoped key), so same-tool/different-profile pairs are not newly flagged (H3).
- Preflight builds `StatusEvent`s through a tolerant local reader (defaults for `at`/`execution_mode`, skips malformed lines); the strict store reader is untouched.
- The reducer's `implementer_of_record` snapshot slot is claim provenance, documented as such in `review_roles.py`.

## 2026-10-07 WP04 (#5721): forced approvals do not restamp the approval bound
- Verified through the real `move-task <WP> --to approved --force` path (CliRunner, real status log) for `approved->approved`, `canceled->approved`, `in_progress->approved`: `force=true`, `review_ref=null`, `review_result=null`, `evidence.review = {reviewer: "unknown", verdict: "approved", reference: "auto-approval:<WP>:<date>"}`. So `evidence` is present on a bare forced move but synthetic; it cannot be the discriminator by presence alone.
- A forced `in_review->approved` DOES attach a `review_result` (reviewer forcing past an unrelated gate). `--self-review-fallback` (for_review->approved, forced) attaches no `review_result` but `evidence.review` with the named reviewer and `--approval-ref`.
- Predicate (`approved_bound._is_forced_review_approval`): counts iff arbiter override over the log strictly before the event, or approved `review_result`, or approved `evidence.review` whose reviewer is not `unknown` or whose reference lacks a synthetic prefix (`review.cycle.SYNTHETIC_REVIEW_REF_PREFIXES`). Attestations and unforced approvals unchanged. Accepted: a forced move that merely names `--reviewer`/`--approval-ref` counts (an asserted, recorded act).
- `consolidation -> review.arbiter`/`review.cycle` imports are lazy and allowed by the layer gates.

## 2026-10-07 WP04 review cycle 1 (#5721): a reviewer name is never evidence
- The first trace ran in an isolated HOME with no git name, so reviewer was `unknown`. `_mt_approval_facts` fills the reviewer with `st.reviewer or _detect_reviewer_name()` (`git config user.name`), so in a real repo a bare `--force` writes a real-looking name and the reviewer discriminator was a no-op. Superseded: reviewer is ignored entirely.
- The evidence reference is `st.approval_ref or synthetic_auto_approval_ref(...)`: non-synthetic only from an explicit `--approval-ref` (and a typed `auto-approval:` prefix is rejected as synthetic). That plus an approved `review_result`, an arbiter override and attestations are the only counting forced approvals.
- `--self-review-fallback` writes the bare evidence on the approval event; `emit_reviewer_self_approval` appends a separate lifecycle event (implementing actor, intended reviewer, failure reason, timestamp) to the mission event log with no event id link. It is the implementer's self-approval, not tied deterministically to the approval event, so it does NOT count; the operator attests (`--attest-approved-reviewed`).

## 2026-10-07 WP05 (#5194): cycle numbers come from every surface a reader consults
- Mechanism confirmed: `create_rejected_review_cycle` resolves the write dir once (COORD under a coordination topology) and `next_cycle_number` globbed only that dir, so a cycle 1 left on PRIMARY (a `local_only` rejection) was invisible and COORD minted cycle 1 again. `ReviewCycleArtifact.write` was a plain `write_bytes`.
- Fix: `_review_cycle_read_candidate_dirs` (cycle.py) lists the dirs `_review_cycle_wp_dir` consults (REVIEW_CYCLE surface plus the PRIMARY fallback); `next_cycle_number(dir, sibling_dirs)` takes max+1 over the union and refuses an unparseable name or a colliding file in any of them. `write` creates exclusively (`open("xb")`) and raises `FileExistsError`; the only src caller is the allocator, so the adopt path is unchanged.
- Not changed: the advertised-path helper (`cycle.py` ~:172) still numbers from one dir.

## 2026-10-07 pre-PR squad fold (#5721): a forced approval is a review only with a claim, an arbiter or an attestation
- Squad finding: with auto-commit on (the default) `_persist_approved_review_cycle` writes an approval `review-cycle-N.md` on every move to approved and the executor rewrites `evidence.review.reference` to its `review-cycle://` pointer, so the "resolvable reference" test counted a bare forced approval as a review. Also `move-task --to in_review --force` then `--to approved --force` attached an approved `review_result`.
- Orchestrator decision: a forced move into `approved` counts as a review approval ONLY when it is (1) an approved-reviewed attestation, (2) an arbiter override (events strictly before it), or (3) a hop out of `in_review` carrying an approved `review_result` where the WP's latest entry into `in_review` was NOT forced (a review claim; `agent action review` records an unforced `for_review -> in_review`). An `evidence.review` reference (incl. `--approval-ref` and `review-cycle://` pointers) and a reviewer name never count for a forced move. Everything else falls back to the newest review approval / `APPROVAL_STAMP_MISSING` and the `--attest-approved-reviewed` route. Supersedes the WP04 predicate above (explicit `--approval-ref` no longer counts).
- The legacy claim shape (`-> in_progress` with `action-review-claim`) never precedes a hop out of `in_review`, so only the `in_review` entry is read.
- 2026-10-07 (close): Final #5721 rule: a forced move into approved is a review only for an approved-reviewed attestation, an arbiter override, or a hop out of in_review whose in_review entry was a genuine (unforced) claim. Evidence references, --approval-ref and reviewer names never count for a forced move; --self-review-fallback and --approval-ref approvals take the attestation route at consolidate.
